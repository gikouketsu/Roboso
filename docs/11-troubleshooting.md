# 11. 故障分析とデバッグ論点

ここでは、当時の報告と現在の公開コードから確認できる問題を、「現象 - コード上の原因 - リスク - 次の確認」の順に整理します。提案する修正は現在の公開ソースに適用済みではありません。

## 1. v1の左旋回とv2のx方向制御が後続分岐で上書きされ得る

**現象の候補**

- x偏差に応じて旋回関数を呼んでも、実際のPWMが後続の分岐によって別の命令に上書きされる可能性がある。

**コード上の根拠**

- v1は左側判定と右側判定が2つの独立した `if` 列です。最初の `left()` の後、2つ目の `else` が `stop()` を呼び得ます。
- v2はx方向の処理後にy方向を別に処理し、yが不感帯内だと `stop()` を呼びます。

**次の確認**

1周期で1つの運動命令だけを決める状態決定層を設け、その後にPWMへ変換するべきです。v3の `if / else if` はx優先の候補ですが、未テストです。

## 2. ボールを見失った後も前の命令が残る

**コード上の根拠**

- 検出可能な輪郭がない場合、Python側はSPIデータを送りません。
- STM32側は受信がないと制御処理を実行せず、コマンドの期限を判定するウォッチドッグを持ちません。

**リスク**

最後のPWM設定が残り、視覚目標がないのに車体が動作を継続する可能性があります。

**次の確認**

- 目標消失を明示する状態フラグを送る。
- STM32で最終正常フレームからの経過時間を測り、期限超過で停止する。
- カメラ切断、プロセス停止、SPI切断を障害注入してPWMを観測する。

## 3. SPIで値は見えるが、フレームの正しさを証明できない

報告にはデータ欠落に対して通信速度を落としたという開発過程の記述があります。一方、公開コードは2 byteを送るだけで、フレームヘッダ、シーケンス番号、CRC、ホスト側のACK照合がありません。

`device.reply(0xAA/0xBB)` は応答値を準備しますが、Pythonは `xfer2()` の戻り値を使いません。したがって「再送付きの信頼性の高い通信」とは評価できません。

## 4. PID式の時間基準が実行周期と一致しない

- Mbed側の `dt` は1 msに固定されています。
- Python側は検出した輪郭ごとに50 ms待機します。
- 制御演算はタイマではなくSPI受信で起動します。

このためI/D項は実時間に対応した値になりません。タイマによる一定周期実行またはマイクロ秒タイムスタンプからの実測 `dt` が必要です。

## 5. 停止出力の意味が版によって異なる

v1/v2は各Hブリッジ入力に `1,1`、v3は `0,0` を出力します。電気的な真理表がないため、brake / coast / 禁止状態のどれに対応するかを公開資料だけで判定できません。実機への書き込み前に、ドライバのデータシートと配線を照合する必要があります。

## 6. 電源降下と不安定動作

報告は開発中に電圧降下と回路の不安定性を問題とし、DC-DCと電源分離を導入したと述べています。ただし、改修前後の電圧波形、電流、リセット回数が残っていないため、根本原因が完全に特定されたとは言えません。
